# 四轮断开时的机构菜单供电模式

用户在VM亮后断电时决定先断开四个底盘电机调试35。当前只需稳定供电读取35菜单，地址/通信方式未知，不发送升降运动。先断总电再拔四轮动力连接，不带电插拔；电源板/外部VM开关仍使用现成电路，不改成外接第二电源。

## 模式及实际工程变更

实际工程D:/新建文件夹4/工创赛/代码/stm32/3.stm32f407工程：

- USER/app_config.h新增APP_ARM_MENU_POWER_TEST=1、ARM_MENU_POWER_TIMEOUT_MS=300000；与旧航向/转动/按键运动模式编译互斥。
- USER/arm_power_mode.c/h独立封装菜单模式判断和供电请求计时。g_arm_menu_power_state为0未请求、1请求有效、2时间已到；不是实际VM电压反馈。
- USER/main.c保留CAN初始化自检，但菜单模式中CAN任务不进入任何底盘轮询/运动命令处理，PC13只消费按键、不创建运动请求。该模式不能执行35电机运动，菜单参数拿到后再接入适当单轴调试模式。
- SYSTEM/SAFETY/safety.c菜单模式只对四轮在线反馈条件作适用范围隔离，保持g_can_guard_ready=0/g_motion_allowed=0，跳过底盘动作状态机/自动停止CAN调度，四轮故意不在线不再导致3秒后断VM。正式模式下原四轮监督与动作监督路径保留。
- 平台任务报告超时、已有fault、CAN内部初始化自检、看门狗、PE2默认关闭、原停止切VM标志、外部VM开关仍保留；不是直接强置PE2或取消全部保护。单次菜单供电最多5分钟，到期按软件任务时间撤销有效请求，必须先把g_vm_test_request=0再1才重新开始。

夹爪180待抓取/140抓取、硬件power.c及FreeRTOS配置未变，不发升降/底盘动作请求。默认g_vm_test_request仍0，不自动开VM；夹爪既有任务启动发送180动作仍保留，不能把菜单模式描述为所有机构均绝无上电动作。

## 验证与使用

完整副本Rebuild与实际工程Build均0错误0警告，Code40672/RO588/RW1528/ZI25368。源码/工程6文件变更，原文件备份、manifest和两次日志位于evidence/p2-arm/2026-10-25/menu-power-mode/。该编译不证明实际VM持续供电或自动断电本轮一定由CAN门触发；原故障码未回传，四轮超时仍只是符合源码的候选。

1. 断电后断开四轮动力连接，保留35当前正确供电/通信连接。
2. 重新打开实际Keil工程，下载本版固件，F5运行；Watch g_vm_test_request设1，外部VM开关保持允许供电位置。
3. 35屏保持亮后直接读ID_Addr、P_Serial、CAN_Baud的现值，发数字或照片，不修改电机参数。
4. 菜单读完将g_vm_test_request设0/关闭原外部开关。若五分钟到期需继续，request先置0等约1秒，再置1。不要按PC13或调用底盘运动；菜单模式暂不提供电机运动功能。

若仍短亮断电，保留fault与state再针对性处理；不反复更改保护条件。
