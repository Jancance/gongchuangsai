# 桌面采集新鲜度诊断

日期：2026-09-26。工程诊断E；不是正式采集模块替换或整车验收。

更新：首次板端记录已复核（`evidence/20260926-020730-481431/`）。主机读取约14.96fps、处理13.56fps，结果主机年龄最大143.09ms，无本轮JPEG警告。读取约15fps的原因尚未确认。增加--buffers显式对照及采集侧耗时记录，下一次测试仅将请求缓冲数由1改4；不改曝光、算法或共享单槽策略。

## 动机与范围

旧颜色audit按read→analyze串行运行，约12～13处理fps；它不能证明30fps采集链里没有积压。项目 `src/smart_carrier/camera.py` 已有最新帧线程骨架，但配置仍未完整实测，且当前诊断需要持续采集中锁参和进程级卡死退出。本次不静默替换现有主流程。

新增 `scripts/p2_freshness_audit.py`。独立子进程拥有相机，在首次read启动采集后写入曝光50/增益30/手动白平衡4600，预热后持续读取。以固定共享内存单槽保存最新解码图、主机read完成时间和软件序号。主进程每次只处理新序号，主动跳过覆盖的帧，不重复处理同一软件序号；这不等于检测了传感器重复帧。

输入或结果相对主机read完成时间超过150ms，记录STALE_INPUT_REJECTED或STALE_RESULT_REJECTED；无新read完成超过500ms结束诊断。150/500ms是本次工程测试参数，不是官方规则或端到端验收阈值。采集阻塞使用进程级终止收尾，启动超时25秒，退出先等待2秒再终止，若发生强制退出写入摘要。无需首次测试就拔USB。

## 输出解释

- host_read_fps：主机成功读入共享槽的速度，不证明摄像头实际唯一帧率。
- processing_fps：颜色分析速度；相比相机快慢由板端实测确定。
- intentionally_skipped_before_processing：软件覆盖或消费间隔导致跳过的序号，不叫USB丢帧。
- input_host_age_ms：主机read完成到开始分析的等待时间。
- result_host_age_ms：主机read完成到分析结束的时间，包含分析耗时。
- 这些时间不包含可验证的曝光起点，不能证明镜头→USB→显示的总延迟；相机/驱动在read前的排队仍需独立诊断。
- CAP_PROP_BUFFERSIZE=1的返回值会保存，但返回成功也不是底层缓冲已经清空的证据。

每轮保存summary.json、逐帧JSONL、首末处理原图、控制读回、分类脚本和诊断脚本哈希；运行时通过2>&1和tee收集JPEG解码stderr。纯视觉诊断，不连接任何电机、串口或动作计数。decoded frame异常也可能仍返回ok，因此本工具不是JPEG完整性检测器。

## 验证状态

本机 `python -m unittest discover -s tests -p test_p2_freshness_diagnostic.py -v` 的4项测试通过：单槽覆盖/序号/时间戳与拷贝独立性；尺寸不匹配不发布；新鲜输入在处理后可过期；阻塞子进程可被终止。--help导入检查通过。

这些只验证工具软件语义，不代表香橙派硬件、跨进程采集实际性能、断线恢复或传感器时间戳能力通过。首次板端测试固定两件物料、不移动相机或灯，正常连接10秒，上传摘要及控制台。若处理后经常过期，应记录并分析，不能直接调高阈值冒充通过。

缓冲诊断更新后共5项本机测试通过，额外模拟验证请求缓冲4、模式读回和采集时间事件。capture_timing中的read_call_ms包括等待及解码，publish_lock_and_copy_ms包括等待共享锁与图像复制；它们不进一步区分内核或传感器耗时。该统计可包含退出过程最后一帧，不能直接等同测量窗口主机帧数。底层缓冲请求与应用单槽是两层概念，增加前者不等于增加后者。
