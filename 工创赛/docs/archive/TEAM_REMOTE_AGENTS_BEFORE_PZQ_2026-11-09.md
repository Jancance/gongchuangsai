# 两人协作与 Codex 开发规则

本文件适用于本仓库全部目录，供两位队员及各自的 Codex 共同遵守。
仓库：`https://github.com/Jancance/gongchuangsai.git`，默认共享分支为 `main`。

## 1. 基本流程与授权

- 每次开发都必须先检查本地状态并从 GitHub 同步最新进度，再开始修改。
- 开发完成后，完成适当验证、更新本地交接记录并报告结果，默认保留本地修改，不自动提交或推送 GitHub。
- 只有用户明确要求“上传 GitHub”“更新到 GitHub”“提交并推送”等时，才执行对应的提交和推送；可以把多次本地开发积累的变更一起交付。
- “修改代码”“更新文档”“继续开发”等普通开发指令不代表上传授权。“更新”一词仅在上下文明显指向 GitHub 时才视为上传指令。
- 用户要求“只看看”“只诊断”“先写草稿”“别上传”等时，以当次要求为准。不得为绕过本地未提交修改而擅自提交推送。
- 报告中区分“本地完成”和“已同步 GitHub”；推送失败须明确报告，不能声称已上传。

## 2. 开发前：同步并了解进度

1. 确认当前目录是本仓库，检查 `git status --short --branch`、当前分支和 `git remote -v`。
2. 如有未提交修改，先检查差异并保留。不得执行清理、覆盖或重置来强行拉取；不得把来历不明的改动直接混入自己的提交。必要时先向用户说明并确认归属。
3. 工作区允许同步时，执行 `git fetch origin`。在 `main` 上用 `git pull --ff-only origin main` 更新；若失败，先分析分叉或冲突，不使用强制覆盖。
4. 如果已有未推送提交，先检查内容及其与远程的关系，再整合远程更新。不能假定本地一定是最新版本。
5. 阅读最新提交、根目录交接文档以及本任务相关的最新文档、证据和源代码，确认队友已完成什么、当前配置是什么、尚缺什么。
6. 同步失败时，先排查。无法取得最新进度须说明原因及同步尚未完成，不把旧代码当作最新版本继续开发。

## 3. 两人同时开发

- 简单的先拉取、后推送不能防止两人同时修改同一个文件。任务开始时先明确各自负责的模块，尽量避免同时改同一文件。
- 若已知队友正在改同一模块，使用任务分支并协调合并；不得直接覆盖队友实现。任务分支也必须从最新远程基线开始。
- 保持提交范围清晰：一项任务对应一个或少量有意义的提交，提交说明写清问题、改动和验证。
- 不擅自改写共享历史，不使用 `git push --force`、`--force-with-lease`、`git reset --hard` 或类似覆盖操作。
- 遇到冲突，逐项理解双方改动后合并并重新验证；无法判断设计意图时向用户确认，不能一律选本地或远程。

## 4. 项目开发约束

- 保留其他人的未提交修改，避免无关重构、批量格式化和批量转码。
- 实际 STM32 工作工程为 `3.stm32f407工程/gongxun-f407.uvprojx`。历史冻结副本 `工创赛/handoff/p1_2026-10-15/firmware/` 不作为当前开发入口。
- 编辑固件前检查原文件编码和换行；保留既有 GBK/CRLF 等格式，避免中文注释损坏。
- 继续遵守子目录中的 `AGENTS.md`。项目规则基线为 `工创赛/docs/competition_requirements_2027.md`：相关工作须核对受影响需求 ID，区分规则事实 R、工程选择 E、待答疑 Q。
- 涉及电机、VM、看门狗和姿态数据时，保留现有故障与停止保护。不能通过清故障、无条件喂狗或绕过保护来伪造测试通过。
- 编译通过、模拟检查、截图和实车观察分别记录。未操作硬件就不能声称已烧录或实测通过。

## 5. 开发后：验证与本地交接

1. 运行与改动相称的构建或检查，查看实际结果；若无法验证，明确记录原因和剩余风险。
2. 更新根目录交接文档 `P1电控组交接_2026-10-15.md` 的当前进度：写明日期、当前配置、完成内容、验证证据、未闭环项和下一步。文件名保留，正文日期持续更新。
3. 审查 `git diff`，确认没有漏改、冲突标记、误转码或无关改动，保留现有未提交成果。
4. 最终回复写清改动、验证结果、未闭环项和下一步，并说明当前仅在本地完成。无需每次询问是否上传。

## 6. 收到明确上传命令后

1. 检查自上次上传以来积累的全部变更，结合本地交接记录确认本次交付范围。不得只上传最后一次修改而遗漏先前已完成且应交付的成果。
2. 审查待提交文件。只提交已确认应交付的变更，不默认把本机缓存、调试布局、构建产物都反复上传；用户明确要求整个文件夹时按其范围检查。
3. 提交前再次 `git fetch origin`，检查队友是否已推送新提交。如有更新，保留本地成果并整合，重新运行受影响的验证。
4. 提交并推送当前交付分支。通常在 `main` 上使用 `git push origin main`；若采用任务分支，须清楚报告分支和待合并状态，不能称其已进入 `main`。
5. 若推送因远程更新被拒绝，重新获取并整合更新、验证后再推送；不得强推。
6. 推送完成后核对远程分支提交与本地提交一致，并检查 `git status`。如仍有未提交、被忽略或未上传的重要交付文件，明确列出，不能把“工作区干净”说成“所有磁盘文件都上传”。
7. 最终回复写清上传范围、最新提交号、远程分支和剩余未上传内容。下一位开发者从第 2 节重新开始。

## 7. Git 操作边界

- 不删除或覆盖队友文件，不擅自更改远程地址、共享分支或仓库可见性。
- 不上传密码、令牌、私钥等凭据。发现此类内容时先隔离相关文件并告知用户。
- 当前仓库包含较多历史资料，首次克隆或大文件推送可能耗时；根据实际进度汇报，不在未核对远程结果时宣布上传成功。
- 若用户明确要求上传整个文件夹，检查 `.gitignore` 是否遗漏应交付文件，并说明实际上传范围；不能只执行 `git add .` 就假定全部文件已包含。
